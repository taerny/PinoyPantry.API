## 1. DTOs — Data Transfer Objects

### The Problem Without DTOs

Your `Product` model maps 1:1 to a database table. If you send it directly from your
controller, you have no control over what goes in or out. Example:

```
Database has: Id, Name, Price, StockQuantity, SupplierCost, CreatedAt
Frontend receives: Id, Name, Price, StockQuantity, SupplierCost, CreatedAt  ← SupplierCost leaked!
```

Also, when a user creates a product, they should NOT be sending `Id` or `CreatedAt`
— those are generated by the server. But if you accept a `Product` directly, nothing
stops them from sending those fields.

### The Solution — Three Separate Shapes

| DTO | Used For | Contains |
|-----|----------|----------|
| `ProductResponseDto` | `GET` — sending data OUT | Only what frontend needs to display |
| `CreateProductDto` | `POST` — accepting data IN | Only what user provides to create |
| `UpdateProductDto` | `PUT` — accepting data IN | Only what user can change |

### Key Rule
> **Your database model is for EF Core. Your DTOs are for the outside world. Never mix them.**

### What You Should Be Able to Do After This Step
- Write all three DTO classes yourself (they're just plain C# classes)
- Explain why each field is or isn't included in each DTO

## 2. Service Layer

### Current Architecture (what you have now)

```
Controller → Repository → Database
```

The controller calls the repository directly. For simple CRUD this is fine to start,
but real-world apps add a **Service layer** in between:

```
Controller → Service → Repository → Database
```

### Why?

The **Repository's job** is: talk to the database. That's it.
The **Service's job** is: business logic. For example:
- "Before saving a product, check if the category is valid"
- "When deleting a product, also delete its related images"
- "Calculate a discounted price based on membership level"

None of that belongs in the controller (too fat) or the repository (wrong concern).

### The Pattern

```
IProductService       ← interface (the contract)
ProductService        ← the actual implementation
```

The controller depends on `IProductService`, never on `ProductService` directly.
This is called **programming to an interface** — it makes code testable and swappable.

### Key Rule
> **Controllers receive requests and return responses. Services contain business logic.
> Repositories talk to the database. Each layer has one job.**

## 3. AutoMapper

### The Problem

Without AutoMapper, every time you convert a `Product` to a `ProductResponseDto`
you write code like this:

```csharp
var dto = new ProductResponseDto
{
    Id = product.Id,
    Name = product.Name,
    Price = product.Price,
    // ... every single field, every single time
};
```

If you have 10 models, you write this 30+ times. It's tedious and error-prone.

### The Solution

AutoMapper reads both classes and maps matching properties automatically.
You define a **Profile** (a mapping config file) once:

```csharp
CreateMap<Product, ProductResponseDto>();
CreateMap<CreateProductDto, Product>();
```

Then in your code:
```csharp
var dto = _mapper.Map<ProductResponseDto>(product);
```

One line. AutoMapper does the rest.

### How `.ForMember()` works — dest vs opt

When property names don't match (e.g. model has `ImageUrll`, DTO has `ImageUrl`), you use:

```csharp
CreateMap<Product, ProductResponseDto>()
    .ForMember(dest => dest.ImageUrl,
               opt => opt.MapFrom(src => src.ImageUrll));
```

- **`dest`** = the **destination** object (the type you're mapping *to*, e.g. the DTO).  
  `dest => dest.ImageUrl` means: "The property I'm configuring on the **result** is **ImageUrl**."

- **`opt`** = **options** for how to fill that property.  
  `opt => opt.MapFrom(src => src.ImageUrll)` means: "Get the value from the **source** (the model) property **ImageUrll**."

- **`src`** = the **source** object (the type you're mapping *from*, e.g. the `Product` model).

So: **dest** = which property on the result; **opt** = how to fill it (e.g. from which source field).  
Matching names are mapped automatically; you only use `.ForMember()` when names differ or you need custom logic.

### Key Rule
> AutoMapper handles **property-to-property** mapping. If the names match, it maps
> automatically. If they don't match, you configure it manually in the Profile.

## 4. FluentValidation

### The Problem

Without validation, a user can POST this:

```json
{ "name": "", "price": -500, "category": null }
```

And your database will happily save it. You could add `if` checks in your controller,
but that gets messy fast and mixes concerns.

### The Solution — FluentValidation

You write a **Validator class** that defines the rules for a DTO:

```csharp
public class CreateProductDtoValidator : AbstractValidator<CreateProductDto>
{
    public CreateProductDtoValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(100);
        RuleFor(x => x.Price).GreaterThan(0);
        RuleFor(x => x.Category).NotEmpty();
    }
}
```

ASP.NET automatically runs this before your controller action fires.
If validation fails, the user gets a `400 Bad Request` with a list of what's wrong —
without you writing a single `if` statement.

### Key Rule
> Validation belongs in the validator, not in the controller or service.

## 5. Swagger / Scalar

### What Is It?

Swagger (or Scalar, the modern replacement) auto-generates a **visual, interactive
API documentation page** from your code. It reads your controllers and models,
and produces a page at `/swagger` or `/scalar` where anyone can:

- See all your endpoints
- See what each endpoint expects and returns
- Test the API directly in the browser (no Postman needed)

### Why It Matters for Your CV

Every real company uses API documentation. Having Swagger on your project shows
you understand professional API development standards.

### Key Rule
> Add Swagger from day one. It takes 5 lines of code and it makes your API
> professional immediately.

## 6. Pagination & Filtering

### The Problem

`GET /api/products` returning ALL products works fine when you have 20.
When you have 2,000, you're sending 2,000 rows over the network every time.
That's slow for the user and expensive on the server.

### The Solution — Query Parameters

```
GET /api/products?page=1&limit=12&category=snacks&search=vinegar
```

Your API returns only the products the frontend currently needs, plus metadata:

```json
{
  "data": [ ...12 products... ],
  "totalCount": 87,
  "page": 1,
  "totalPages": 8
}
```

### The Pattern

You'll create a `ProductQueryParams` class:

```csharp
public class ProductQueryParams
{
    public int Page { get; set; } = 1;
    public int Limit { get; set; } = 12;
    public string? Category { get; set; }
    public string? Search { get; set; }
}
```

The controller accepts this as a parameter and passes it to the service.

### Key Rule
> Never return unbounded lists from an API. Always paginate.

## 7. Global Exception Handling

### The Problem Without It

If something crashes in your service or repository, ASP.NET returns a raw `500` error
with a full stack trace — including internal file paths and code details.
That is a **security risk** in production.

### The Solution — Middleware

A single piece of middleware wraps every request. If anything throws an unhandled
exception, the middleware catches it and returns a clean, consistent response:

```json
{
  "status": 500,
  "message": "An unexpected error occurred.",
  "traceId": "abc123"
}
```

Your controllers stay clean — no try/catch blocks scattered everywhere.

### Key Rule
> Handle expected errors (e.g. "product not found") in your service with proper
> result types. Handle unexpected errors globally with middleware.

## 8. Seed Data

### What Is It?

Seed data is a set of records that gets inserted into the database automatically
when it's empty. This means anyone who clones your project (or you on a new machine)
gets a working database with real data immediately.

### How It Works in EF Core

You override `OnModelCreating` in your `ApplicationDBContext` and call `entity.HasData(...)`.
EF Core includes this in your migrations.

### Why It Matters

For your portfolio site, you need actual products showing on the page.
We'll import your existing CSV data into the seed.

## 9. Git & GitHub — Branching Strategy

### The Strategy: Two Main Branches

```
main    ← production-ready code only. Every push here = deploys to Azure.
dev     ← your working branch. You code here.
```

### Your Daily Workflow

```bash
# Always start from dev
git checkout dev

# Create a feature branch
git checkout -b feature/add-dtos

# Do your work, commit often
git add .
git commit -m "feat: add ProductResponseDto and CreateProductDto"

# When done, merge back to dev
git checkout dev
git merge feature/add-dtos

# When dev is stable and tested, merge to main (triggers deploy)
git checkout main
git merge dev
git push origin main
```

### Commit Message Convention

Use this format — it's called **Conventional Commits** and it's industry standard:

```
feat: add pagination to products endpoint
fix: correct CORS origin URL
refactor: extract product logic into service layer
docs: update README with setup instructions
chore: add gitignore entries
```

### Key Rule
> Never code directly on `main`. Always branch off `dev`.

## 10. GitHub Actions — CI/CD

### What Is CI/CD?

- **CI (Continuous Integration):** Every time you push code, automatically build it
  and run tests to catch broken code early.
- **CD (Continuous Deployment):** If CI passes, automatically deploy to Azure.

### Your Pipeline Will Look Like This

```
You push to main
        ↓
GitHub Actions triggers
        ↓
Step 1: Restore NuGet packages
Step 2: Build the .NET project
Step 3: Run tests (when you have them)
Step 4: Publish to Azure App Service
```

All of this is defined in a single YAML file at `.github/workflows/deploy-api.yml`.

### Why It Matters for Your CV

CI/CD knowledge is one of the most in-demand junior skills right now.
Most juniors don't have it. Having a working pipeline in your GitHub repo is
a strong differentiator.

### Key Rule
> Your pipeline is only as useful as your tests. A pipeline with no tests just
> automates deploying broken code faster. Add at least basic tests.

## 11. Azure — What Each Service Does

### Azure App Service (Free F1 Tier)
**What it is:** A managed hosting environment for web apps. You don't manage servers —
you just deploy your code and Azure runs it.

**Hosts:** Your .NET API

**Free tier limits:**
- 60 CPU minutes per day
- 1 GB RAM
- App "sleeps" after 20 minutes of inactivity (cold start ~10 seconds)
- Fine for a portfolio project

**URL:** `your-api-name.azurewebsites.net`

---

### Azure Static Web Apps (Free Forever)
**What it is:** Hosting for static frontends (HTML, CSS, JS). React apps are static
after you run `npm run build` — the output is just files.

**Hosts:** Your React frontend

**Free tier includes:**
- Custom domain support
- SSL certificate (HTTPS) for free
- Global CDN
- GitHub Actions integration built in

**URL:** `your-app-name.azurestaticapps.net`

---

### Azure SQL Database (Free Offer)
**What it is:** Managed SQL Server in the cloud. No installation, no maintenance.

**Hosts:** Your products database

**Important:** Azure SQL is not the same as your local `SQLEXPRESS`. The connection
string will change when you deploy. You'll store the production connection string
as a **Secret** in GitHub and an **Environment Variable** in Azure — never in code.

---

### The Golden Rule of Cloud Config
> **Never hardcode connection strings, API keys, or secrets in your code.**
> Use environment variables locally, GitHub Secrets in CI/CD, and Azure App Settings
> in production. Your `appsettings.json` is for non-sensitive config only.
